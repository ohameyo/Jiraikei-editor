# 蕾蕾卡哇 iOS 壳版 App V1 规格

Date: 2026-07-06

## Goal

把现有正式版网页编辑器包装成一款可上架的 iOS App，V1 只解决“用户能在手机 App 里导入图片、完成现有编辑、保存或分享成图”的闭环。

V1 不重做编辑器，不实现 Live Photo，不做社区、电商、账号系统或创作者平台。

## Product Positioning

App 名称：蕾蕾卡哇

一句话定位：日系量产型图片编辑器

对外描述重点：

- 日系、量产型、可爱风图片编辑。
- 支持滤镜、贴纸、文字、相框、覆膜和基础调色。
- 适合自拍、穿搭、探店、社交头像和小红书配图。

App Store 文案避开“地雷系”等可能造成审核误解的表达。JiraiKawa 继续作为英文品牌和域名资产存在，但中文上架表达以“蕾蕾卡哇”为主。

## Recommended Approach

V1 采用“混合 App”方案。混合 App 指一部分能力用网页实现，一部分能力用原生 iOS 实现。

核心结构：

- iOS 原生外壳负责相册权限、图片选择、保存到相册、系统分享和上架所需配置。
- WKWebView 承载现有网页编辑器。WKWebView 是 iOS 内置网页容器，可以在 App 内运行网页。
- JS Bridge 连接网页和原生层。JS Bridge 是 JavaScript 和 iOS 原生代码之间互相传消息的通道。

这个方案比“纯网页套壳”更稳，因为它给了 App Store 审核能看见的原生价值；也比“完全重写原生编辑器”更快，因为复用现在已经跑通的正式版编辑器。

## Alternatives Considered

### A. 纯 WebView 套壳

优点是最快，几乎只把网站放进 App。

问题是 App Store 可能认为它只是网站包装，原生价值不足；同时相册保存、分享、权限和后续 Live Photo 能力都不好扩展。

### B. V1 混合 App

优点是上线速度和产品完整度比较平衡。现有网页能力继续复用，同时把导入、保存、分享这些手机用户强依赖的环节交给原生系统。

这是 V1 推荐方案。

### C. 完全原生重写

优点是长期上限最高，后续 Live Photo、视频、相册深度能力最好做。

问题是周期长、成本高，还会重复实现现有网页端已经成熟的滤镜、贴纸、文字、图层、导出逻辑。V1 不采用。

## V1 Must Have

V1 必须包含以下能力：

- App 启动后直接进入编辑器，不做营销首页。
- 加载现有正式版或 Lab 验证后的网页编辑器。
- 支持从 iPhone 相册选择静态图片导入编辑器。
- 支持使用现有网页端的滤镜、贴纸、文字、相框、覆膜、马赛克、人像散红和导出能力。
- 支持把最终静态图片保存到 iPhone 相册。
- 支持调用 iOS 系统分享面板。系统分享面板是 iPhone 内置的分享菜单，例如发到微信、保存到文件或发送给朋友。
- 支持基础错误提示：图片导入失败、保存失败、网络不可用、相册权限未授权。
- 支持 App Store 上架所需的基础信息、隐私说明、图标、启动页和截图。

## V1 Explicitly Out Of Scope

以下内容明确不进 V1：

- Live Photo 导入、预览、编辑和导出。
- 视频导入、视频滤镜和视频导出。
- 完全原生编辑器重写。
- 离线完整编辑能力。
- 用户账号、登录、云同步和会员系统。
- 社区、模板投稿、创作者后台和电商。
- 推送通知。
- 多语言。
- iPad 专门布局。
- Android 版本。
- App 内购买。App 内购买指通过 Apple 支付购买会员、素材包或功能。

## App Behavior

### Launch

打开 App 后进入编辑器主页。首屏要像工具，不像官网。

如果网络正常，加载当前生产网页或指定 App 专用网页入口。App 专用网页入口可以和正式版共享代码，但需要允许 App 判断运行环境。

如果网络异常，显示一个原生错误页，提供重试按钮。

### Import

用户点击导入图片时，V1 优先调用 iOS 原生相册选择器，而不是只依赖网页上传控件。

选择完成后，原生层把图片传给网页编辑器。网页编辑器接收到图片后，走现有的导入和编辑流程。

如果用户取消选择，不改变当前编辑状态。

### Edit

编辑能力以当前网页正式版为准。V1 不为了 App 单独改变滤镜算法、贴纸系统、文字系统或图层逻辑。

任何编辑器改造仍然按现有流程先部署 Lab，再确认是否进入正式版或 App 专用入口。

### Export

用户点击导出或保存时，网页端生成最终静态图片。原生层接收导出图片后提供两个动作：

- 保存到相册。
- 打开系统分享面板。

V1 导出的结果是静态图片，格式优先使用 PNG 或 JPEG，具体沿用网页端当前导出策略。

## Live Photo Boundary

V1 不支持 Live Photo。

Live Photo 是 iPhone 的动态照片格式，本质上包含一张静态照片和一段短视频。要可靠导出为系统识别的 Live Photo，需要 iOS 原生照片框架参与，不是单纯网页可以稳定完成的能力。

后续 Live Photo 可以作为 V2 技术专项，独立验证：

- 只对滤镜、相框、覆膜这类全画面效果做动态照片支持。
- 一旦用户添加贴纸、文字、局部马赛克或需要逐帧识别的人像散红，就默认导出静态图片。
- 人像散红如果要用于 Live Photo，需要逐帧或关键帧渲染，V1 不承担这个复杂度。

## Technical Architecture

### Native iOS Layer

原生 iOS 层负责：

- 创建 WKWebView。
- 配置 App 权限和 Info.plist。Info.plist 是 iOS App 的配置文件，用来声明权限文案、名称和系统能力。
- 调用 PHPicker 选择图片。PHPicker 是 Apple 提供的系统相册选择器。
- 调用 Photos 保存图片到相册。Photos 是 Apple 的相册框架。
- 调用 Share Sheet 分享图片。Share Sheet 是 iOS 系统分享面板。
- 暴露 JS Bridge 消息接口。

### Web Editor Layer

网页编辑器负责：

- 当前所有图片编辑 UI。
- 图片处理和画布渲染。
- 素材、贴纸、滤镜和导出逻辑。
- 区分普通浏览器和 App 环境。

### Bridge Contract

V1 需要约定最小消息协议：

| Direction | Message | Purpose |
| --- | --- | --- |
| Web to native | `pickImage` | 请求打开系统相册 |
| Native to web | `imagePicked` | 返回用户选择的图片 |
| Web to native | `saveImage` | 请求保存导出图片 |
| Native to web | `saveResult` | 返回保存成功或失败 |
| Web to native | `shareImage` | 请求打开系统分享 |
| Native to web | `nativeError` | 返回原生错误 |

消息体只传必要字段：图片数据、文件名、MIME 类型、错误码和用户可读提示。MIME 类型是图片数据的格式标识，例如 `image/png` 或 `image/jpeg`。

## Web Deployment Strategy

V1 可以先用远程网页入口，便于快速验证和修复：

- Lab App 测试时加载 Lab 入口。
- 上架候选版本加载正式版或 App 专用正式入口。

为了降低审核和运行风险，App 专用入口需要满足：

- 不出现浏览器式导航。
- 不依赖外部跳转完成核心编辑流程。
- 素材数据更新后能处理缓存，避免手机端长期看不到新素材。

后续如果需要更强稳定性，可以把网页静态资源打包进 App，但 V1 不默认这么做。

## Analytics

V1 继续使用现有匿名埋点。匿名埋点指不采集真实身份，只用随机访客 ID 统计使用情况。

V1 至少需要区分：

- `app_open`：App 打开。
- `image_import`：图片导入成功。
- `image_export`：图片导出成功。
- `save_to_album`：保存到相册成功。
- `share_open`：打开系统分享。

DAU 指 Daily Active Users，也就是日活跃用户数。V1 的 DAU 继续用现有匿名访客 ID 统计，不用 IP 作为用户身份。IP 是网络地址，用它识别用户不稳定，也有隐私和合规风险。

## Privacy And Compliance

V1 的隐私边界：

- 不需要账号。
- 不上传用户照片到业务服务器，除非未来明确做云功能。
- 仅在本机完成编辑和保存。
- 需要申请相册读取和写入相关权限。
- 需要准备隐私政策页面和技术支持页面。
- App Store 隐私问卷中如实填写匿名分析数据和相册访问用途。

权限文案要清楚解释：

- 读取相册：用于选择要编辑的图片。
- 保存相册：用于保存编辑后的图片。

## App Store Preparation

V1 上架前需要准备：

- App 名称：蕾蕾卡哇。
- Subtitle：日系量产型图片编辑器。Subtitle 是 App Store 名称下面的一行短描述。
- App icon：1024 x 1024 图标。
- 启动页。
- iPhone 截图，至少覆盖导入、编辑、贴纸/滤镜、导出结果。
- 隐私政策 URL。
- 技术支持 URL。
- App Review Notes。App Review Notes 是给 Apple 审核员看的说明，解释 App 怎么用、是否需要账号、核心功能在哪里。
- 测试账号不需要，因为 V1 没有登录。

审核说明重点：

- 这是图片编辑工具。
- 用户可以从相册导入照片。
- 用户可以在 App 内编辑图片。
- 用户可以保存或分享编辑后的结果。

## Execution Phases

### Phase 0: Product And Review Prep

目标：把上架边界和素材准备好。

产出：

- 本规格文档。
- App Store 名称、副标题、关键词和描述初稿。
- 隐私政策草案。
- 支持页面草案。
- 截图清单。

验收：

- V1 范围不再临时加入 Live Photo、社区或会员。
- App Store 表达不使用高风险定位词。

### Phase 1: iOS Shell Prototype

目标：证明现有网页编辑器可以在 App 里稳定跑起来。

产出：

- 一个最小 iOS 工程。
- WKWebView 加载 Lab 入口。
- 网络错误重试页。
- App 内基础导航和返回保护。

验收：

- 真机能打开编辑器。
- 能完成一次网页端已有的图片导入、编辑和导出流程。
- 记录已发现的 WebView 兼容问题。

### Phase 2: Native Import, Save, Share

目标：把 App 和 iPhone 相册能力接起来。

产出：

- 原生相册选择。
- 原生保存到相册。
- 系统分享面板。
- JS Bridge 最小协议。

验收：

- 真机从相册选择图片后进入编辑器。
- 编辑后能保存到相册。
- 编辑后能打开系统分享。
- 权限拒绝、取消选择、保存失败都有可理解提示。

### Phase 3: App Polish And Analytics

目标：让它像一个完整 App，而不是浏览器窗口。

产出：

- App 图标和启动页。
- App 环境下的导入、保存、分享按钮文案和状态优化。
- App 事件埋点。
- 基础崩溃和错误记录方案。

验收：

- App 打开、导入、导出、保存、分享事件可查。
- iPhone 主流尺寸上没有明显布局遮挡。
- 弱网和离线状态有兜底提示。

### Phase 4: TestFlight

目标：先用 Apple 官方测试渠道验证。

TestFlight 是 Apple 的 App 测试分发工具，可以给内部或外部测试用户安装未正式上架的版本。

产出：

- TestFlight 构建。
- 内测说明。
- 反馈表或反馈收集方式。

验收：

- 至少完成多台真机测试。
- 能稳定完成导入、编辑、保存、分享。
- 明确是否有审核前必须修的问题。

### Phase 5: App Store Submission

目标：提交第一个可审核版本。

产出：

- App Store Connect 信息。App Store Connect 是 Apple 管理 App 上架、截图、版本和审核的平台。
- 截图、描述、隐私问卷和审核说明。
- 提交审核的构建包。

验收：

- 审核包不包含 Live Photo 等未完成承诺。
- 审核说明能让审核员在 1 分钟内完成核心路径。
- 被拒后只处理明确拒审点，不顺手扩大 V1 范围。

## Initial Schedule

建议节奏：

- 第 1-2 天：确认规格、完成 App Store 文案和隐私政策草案。
- 第 3-5 天：做 iOS 壳版原型，真机跑通网页编辑器。
- 第 6-9 天：接原生导入、保存、分享。
- 第 10-12 天：修 WebView 兼容问题、补埋点、准备截图。
- 第 13-15 天：TestFlight 内测和上架材料整理。

如果过程中发现 WebView 兼容问题较多，优先保证静态图片导入、编辑、保存闭环，不提前加入 Live Photo 或社区能力。

## Risks

- App Store 认为 App 原生价值不足。缓解方式是 V1 必须提供原生相册导入、保存和系统分享。
- WebView 和 Safari 表现不完全一致。缓解方式是真机测试关键路径，不只看浏览器。
- 远程网页缓存导致素材更新不同步。缓解方式是给 App 入口增加版本化资源策略。
- 图片过大导致内存压力。缓解方式是限制导入尺寸或在导入时压缩。
- 权限文案不清导致用户拒绝授权。缓解方式是权限前置说明和失败兜底。

## Deferred Roadmap

V2 候选：

- Live Photo 技术验证。
- App 专用缓存策略。
- 模板库。
- App 内素材包更新体验。
- 基础收藏和最近使用。

V3 候选：

- 创作者素材投稿。
- 模板共创。
- 用户作品社区。
- 账号系统和云同步。
- 商业化素材包或品牌合作。

## Decision Summary

V1 的边界是“能上架、能用、能证明用户愿意在 App 里编辑图片”。

所有超出静态图片编辑闭环的能力都不进入 V1。蕾蕾卡哇先作为图片编辑器站稳，再逐步长成素材、模板、创作者和社区产品。
