# 后续事项讨论与推进

## 优先级
P1，作为下一阶段产品和工程事项的总控讨论入口。

## 任务目的
为 Jirai-editor 后续事项新开一个独立子任务，用来收敛滤镜开发优化、贴纸改色功能、小程序/轻 App 封装等中长期方向。

本任务不替代现有专项任务，而是作为上层路线图：
- 先判断哪些事情值得做、先后顺序是什么。
- 再把可执行事项拆回具体专项任务。
- 避免滤镜、贴纸、封装、性能和部署讨论混在单次 bug 修复里。

## 讨论范围
### 滤镜开发优化
- 新滤镜风格方向：地雷系、病弱感、冷白皮、棚拍感、灰粉黑白、低饱和但保留唇色和腮红。
- 现有滤镜稳定性：不同光线、肤色、黑发、红色小物、白墙、暗光照片下的表现。
- 滤镜参数训练流程：样张库、对比图、验收标准、版本记录。
- 滤镜实时预览体验：拖动中是否需要完全等同最终效果、是否允许低成本近似预览。
- 与现有任务关系：
  - 参数审美和色彩安全继续落在 `tasks/filter-training-v2.md` / `tasks/filter-parameter-tuning.md`。
  - 渲染卡顿和架构优化继续落在 `tasks/filter-render-performance.md` / `tasks/canvas-render-architecture-spike.md`。

### 贴纸改色功能
- 支持对象：优先考虑 PNG 贴纸、手绘贴纸、装饰贴纸；暂不默认覆盖马赛克和文字。
- 改色方式候选：
  - 主色替换：识别贴纸主色，把粉色/蓝色/黑色等替换为用户选择色。
  - 色相旋转：保留明暗和透明度，只改变整体色相。
  - 分区改色：未来支持对描边、填充、高光分开调色，但初期不建议做太复杂。
- UI 入口候选：
  - 选中贴纸后在图层控制器显示「贴纸颜色」。
  - 保留「恢复原色」按钮。
  - 可选一组常用色 swatch：粉、蓝、黑、白、紫红。
- 技术注意：
  - 预览和导出必须一致。
  - 不能破坏透明边缘、阴影和白色描边。
  - 需要缓存改色结果，避免每次拖动或渲染都重新逐像素处理。
  - 贴纸缩略图是否同步改色需要单独决策，初期可以只改画布实例。

### 小程序与轻 App 封装
- 小程序方向已明确为微信小程序，需单独评估，不直接等同于 PWA 或 Capacitor。
- 微信小程序不是现有静态网页的简单封装，应按“微信小程序迁移/重写成本”评估。
- 微信小程序关键风险：
  - Canvas API 与浏览器 Canvas 差异，尤其逐像素滤镜、图层合成、导出画质和性能。
  - 图片导入、临时文件、跨域/下载域名、保存到相册权限和用户授权流程。
  - 字体、贴纸、拍立得边框等静态资源包体积限制，以及分包/远程资源策略。
  - 当前 DOM、CSS、浏览器 Canvas、Pointer/Touch 事件模型无法直接迁移，可能需要较大重写。
  - 微信内调试、真机预览、基础库版本和 iOS/Android 微信客户端差异需要单独验收。
- 推荐路线：
  1. 先稳定 Web 正式版核心体验。
  2. 做 PWA/缓存/安装体验试验。
  3. 再做 Capacitor WebView 小样，验证图片导入、Canvas 渲染、保存到相册。
  4. 微信小程序只在确认需要微信生态分发时开启 spike，并按“重写成本”而不是“简单封装”评估。

## 初步优先级建议
1. 滤镜开发优化：最高优先级。滤镜是核心审美能力，也最影响用户第一感受。
2. 贴纸改色功能：中高优先级。能增加可玩性，但需要控制范围，先做单个贴纸实例改色。
3. PWA / App 封装验证：中优先级。用于验证安装、缓存、保存体验，不急于正式 App 化。
4. 微信小程序：暂缓到 spike。当前更像潜在新平台项目，不能假设现有网页可低成本迁移。

## 可拆分子任务草案
- `滤镜样张库与验收表`：整理典型自拍、暗光、白墙、黑发、红色配饰样张和每个滤镜目标。
- `贴纸改色 MVP`：选中贴纸后支持主色改色、恢复原色、导出一致。
- `贴纸改色性能缓存`：缓存改色后的 ImageBitmap/canvas，减少重复像素处理。
- `PWA 安装与缓存试验`：承接 `tasks/pwa-installability.md`。
- `Capacitor 保存到相册 spike`：只验证 WebView 导入、Canvas 导出、保存链路。
- `微信小程序迁移可行性 spike`：评估重写范围、资源限制、微信 Canvas API、图片导入和保存到相册链路。

## 当前结论
- 后续推进不应直接从“小程序封装”开始。当前 Web 仍是最高性价比的产品验证载体。
- 滤镜优化应该继续作为产品核心线推进，并保留可复现样张和参数记录。
- 贴纸改色适合做成小而完整的 MVP：选中贴纸、改一个颜色、导出一致、可恢复。
- 微信小程序更像单独平台适配项目，需要等 Web 核心功能稳定后再决定。

## 2026-05-21 路线拆解结论

### 与现有任务关系
- 滤镜开发优化不是新建独立大任务，而是继续拆入：
  - `tasks/filter-training-v2.md`：样张库、审美目标、参数记录、AB 验收。
  - `tasks/filter-parameter-tuning.md`：最终滤镜效果、HSL、肤色/红色/黑发安全边界。
  - `tasks/filter-render-performance.md` / `tasks/canvas-render-architecture-spike.md`：拖动、缓存、Worker、分层渲染等性能与架构问题。
- 贴纸改色目前没有专项任务，适合从本讨论任务沉淀出一个小 MVP 任务；它不应混入 `tasks/mosaic-sticker-shapes.md`，后者主要负责贴纸/马赛克比例、预览、素材包和缩略图。
- PWA / App 封装已经有专项边界：
  - `tasks/pwa-installability.md`：PWA 安装、离线、Service Worker 和缓存试验。
  - `tasks/app-wrapper-spike.md`：Capacitor / Tauri / Electron 等封装可行性。
  - 微信小程序不等同于上述二者，应只作为单独 spike 候选，并按微信生态分发诉求和迁移成本评估。

### 优先级排序
1. 滤镜开发优化：最高优先级。滤镜是核心审美和用户第一感受，但近期应先做样张/验收流程与性能边界确认，避免继续只靠单次参数手感调。
2. 贴纸改色功能：第二优先级。它是可控的玩法增量，适合做成小 MVP；需要先 spike 素材改色算法和导出一致性，再决定是否进入完整 UI。
3. PWA / App / 微信小程序封装：第三优先级。PWA 可在 Web 核心稳定后低成本试验；Capacitor 等 App 壳需要等 PWA 和性能基线明确；微信小程序暂缓，只在微信生态分发诉求明确后做迁移成本 spike。

### 近期可做
- 滤镜样张库与验收表：建立固定样张矩阵、每个预设目标、失败类型和评分记录。
- 滤镜运行入口对齐：确认 `src/app.js` 与 `src/config/filterPresets.js` 的职责，避免参数记录和实际运行不一致。
- 贴纸改色技术 spike：只验证 2-3 个代表性 PNG 贴纸的主色替换、色相旋转、透明边缘/白边/阴影保护、导出一致。

### 需要 spike
- 滤镜渲染架构 spike：Worker / OffscreenCanvas / 分层合成 / 缓存底图能否解决 lab 后仍无质变的问题。
- 贴纸改色缓存策略：改色后的 canvas / ImageBitmap 缓存粒度、历史记录、导出路径复用。
- PWA 安装与缓存试验：manifest、Service Worker、资源版本失效、iOS Safari 限制。
- Capacitor 保存到相册 spike：只验证导入、Canvas 导出、保存和分享链路。
- 微信小程序迁移可行性 spike：仅评估迁移/重写范围、资源限制、Canvas 能力、图片导入和保存到相册链路，不进入实现。

### 暂缓
- 直接封装正式 App。
- 直接做微信小程序迁移。
- 贴纸分区精细改色、缩略图同步改色、批量改色。
- 在没有样张库和验收表前大范围新增滤镜预设或继续堆复杂参数。

### 推荐下一轮任务
1. 先做「滤镜样张库与验收表」。它不依赖功能代码，能立刻提高后续滤镜调参和性能优化的判断质量。
2. 同步或随后做「贴纸改色技术 spike」。范围控制在素材算法验证，不先做完整 UI，能快速判断 MVP 是否值得进入实现。

### 需要确认
- 滤镜样张是否由用户提供真实照片/参考图，还是先用本地临时测试图建立表格结构。
- 贴纸改色第一版更偏向“主色替换”还是“整体色相旋转”。
- 改色入口是否只在选中贴纸实例后显示，是否需要支持恢复原色。
- PWA / App 的目标更偏“可安装图标和离线打开”，还是“保存到相册/系统分享”。
- 微信小程序是否是近期真实分发目标，还是先作为中长期备选路线记录。
