# 网页制作方向与 App 封装方案

## 优先级
P1，后续产品与工程路线讨论任务。

## 任务目的
为 Jirai-editor 后续制作方向建立一个独立讨论入口，避免和当前 P0「整站丝滑性与跟手优化 v2」混在一起。

本任务重点讨论：
- 网页性能优化路线。
- 功能优化和产品取舍。
- Web 版本工程结构演进。
- PWA、移动端网页、内嵌浏览器适配。
- 后续封装成 App 的技术方案。
- 上线、部署、缓存、资源体积和兼容性策略。

本任务当前只做方向讨论和方案沉淀，不直接改动具体功能代码。

## 讨论范围
### 网页性能
- 首屏加载速度、资源体积、图片和字体加载策略。
- Canvas 渲染主线程压力、Worker / OffscreenCanvas 可行性。
- 低端手机和内嵌浏览器性能基线。
- 滤镜、贴纸、文字、马赛克、腮红等模块的长期性能分层。
- 静态资源缓存、版本号、Service Worker / PWA 缓存策略。

### 功能优化
- 当前功能是否继续做加法，还是围绕核心修图路径做减法。
- 滤镜参数、贴纸、文字、马赛克、腮红的产品优先级。
- 移动端和 PC 端是否保持完全一致功能，还是做差异化。
- 导出、保存草稿、历史记录、预设管理等中长期功能。
- 用户使用路径是否更像工具型网页、轻 App，还是内容创作器。

### 工程结构
- 是否继续保持单页静态项目，还是逐步模块化/构建化。
- 当前 `src/app.js` 过大的拆分策略。
- Canvas 渲染、交互层、UI 控件、状态管理的边界划分。
- 测试方式：静态检查、浏览器回归、真机验收清单。
- 未来是否引入构建工具、TypeScript、组件框架或保持原生方案。

### App 封装方向
- PWA：成本最低，适合先验证安装体验和离线缓存。
- Capacitor / Tauri / Electron：根据目标平台选择封装壳。
- iOS / Android WebView：需要重点评估文件选择、导出保存、内存、Canvas 性能。
- 原生重写：成本最高，只有在 Web 性能或系统能力无法满足时再考虑。
- 封装 App 前必须先明确：核心性能瓶颈、目标平台、分发方式、是否需要账号/云端能力。

## 初步判断
- 近期不建议马上进入 App 封装。当前最影响体验的是移动端渲染与操作跟手，应该先把 Web 核心体验稳定下来。
- 第一阶段应继续做 Web 版性能和功能收敛，让用户在浏览器里已经觉得顺手。
- 第二阶段可以做 PWA/桌面安装体验验证，成本低，也能提前暴露缓存、文件权限、离线和导出问题。
- 第三阶段再评估 Capacitor 等封装方案，重点看移动端 WebView 中 Canvas、图片导入和导出保存是否稳定。

## 2026-05-02 结论
### 近期是否封装 App
近期不建议直接封装 App，应继续打磨 Web。

理由：
- 当前核心瓶颈不是浏览器入口形式，而是 Web 内部的主线程 Canvas 渲染、资源体积、交互期间渲染分层和工程结构债。直接套 App 壳会把这些问题带进 WebView。
- 目标体验是轻量、移动端可用、可快速分享/打开，Web 版本天然更适合先验证核心修图链路。
- App 壳只在明确出现浏览器无法满足的需求时才有价值，例如稳定保存到相册、离线安装、系统分享、文件权限、桌面菜单、素材本地缓存等。
- 当前应先把 Web 做到“在 Safari/Chrome/微信/小红书内嵌浏览器中足够快、足够稳”，再判断 PWA 或 Capacitor 是否必要。

推荐顺序：
1. Web 性能和功能收敛。
2. PWA 低成本验证安装、离线和缓存策略。
3. Capacitor 移动端壳小样验证。
4. 只有在桌面分发明确成立时再评估 Tauri/Electron。
5. 原生重写暂缓，除非 WebView 的 Canvas、内存或保存能力被真实验证为不可接受。

## 当前 Web 技术形态
### 产品状态
- 目前是静态单页网页：`index.html` 直接加载 `styles.css` 和 `src/app.js`，无打包构建流程。
- 核心能力已集中在一个页面内：图片导入、滤镜、人像腮红、马赛克、贴纸、文字图层、图层控制、前后对比和导出。
- PC 与移动端共用同一套主逻辑，样式通过 CSS 适配；移动端已围绕滑杆、图层 dock、overlay 操作做过多轮优化。
- 已有埋点入口 `functions/analytics.js` 和 `/analytics` 端点设定，但整体仍偏静态网页。

### 工程状态
- `src/app.js` 是实际主入口，约 5700 行，包含状态、滤镜配置、字体加载、渲染、事件、UI 控件、导出和 overlay 交互。
- `src/main.js`、`src/core/store.js`、`src/modules/*`、`src/ui/controls.js` 已存在模块化方向，但当前 `index.html` 没有使用模块入口，模块实现也与 `src/app.js` 内部实现存在明显代差。
- 这意味着后续维护风险不是“没有模块”，而是“真实入口和模块化草稿并存”，容易误改旧模块或重复实现。
- 当前验证方式以 `node --check src/app.js` 和人工浏览器/真机验收为主，缺少可重复的性能基线和浏览器回归脚本。

### 资源状态
- `assets` 约 49MB，其中 `assets/fonts` 约 47MB，是最大加载/缓存风险。
- 贴纸资源约 1.6MB，单个资源体积相对可控。
- 代码没有构建拆包，首屏会直接下载主 CSS/JS；字体加载在代码内已有移动端子集和延迟加载策略，但资源目录仍需要上线层面的缓存和延迟策略。

## 主要技术债
- `src/app.js` 过大且职责混合：产品配置、渲染算法、状态管理、DOM UI、事件处理和导出混在同一个文件中。
- 模块化文件与真实入口不一致：`src/main.js` 和 `src/modules/*` 不能视为当前生产实现来源，需要先确立迁移策略。
- 主线程逐像素处理仍是核心压力点：HSL、肤色保护、腮红、黑发保护、暗部平滑等会在大图和低端机上造成阻塞。
- 临时 canvas 和 ImageData 使用频繁，可能带来 GC 抖动和内存峰值。
- 移动端交互已做降级预览，但真实渲染仍是同步长任务，释放滑杆/图层时可能出现等待、跳变或短暂卡顿。
- 缺少明确的兼容性矩阵：Safari、Chrome、微信、小红书内嵌浏览器、低端 Android WebView 的差异需要单独记录。
- 缺少上线资产策略：字体、贴纸、版本号、Service Worker、缓存失效、CDN headers 需要在部署任务里明确。

## 性能瓶颈优先级
1. 主线程滤镜渲染：优先拆分“交互预览”和“最终清晰渲染”，明确哪些参数拖动中只做 CSS/低分辨率近似，哪些只在松手后执行。
2. 渲染缓存和临时 canvas 复用：减少全量重建、减少 `getImageData`/`putImageData` 频率，控制内存峰值。
3. 字体和素材加载：首屏只加载最低必要资源，文字字体按需加载，重字体必须延迟或子集化。
4. 移动端 WebView 验收：建立固定机型/浏览器清单，记录滑杆、overlay、导出保存、键盘、旋转屏幕表现。
5. 部署缓存策略：静态资源强缓存，HTML 短缓存，资源文件名或查询版本明确失效。

基于 UX Lab 结果，P0 性能优化需要重新分层：
- 保底层：修复具体可见卡点和残影，例如释放瞬间旧位置闪回、CSS 预览清除空窗、overlay 控制器重建。
- 架构层：验证是否能把 `applyTonePipeline()` 从主线程交互路径里移走，或把最终合成变成“缓存底图 + 轻量图层合成”。
- 产品层：把重效果明确标为松手生效，拖动中只显示可信的快速预览，不追求每个参数都实时高保真。

## 功能加法/减法策略
### 应该先做
- 保持核心路径短：导入图片 -> 选滤镜/微调 -> 加少量贴纸/文字/马赛克 -> 对比 -> 导出。
- 对高频控制做产品收敛，移动端只显示最有价值的参数；低频、高风险、高性能成本的细项放到高级区或暂缓展示。
- 优先完善导出成功率和保存体验，因为这是修图工具的闭环。
- 以埋点验证功能价值：工具点击、上传成功、预设使用、导出预览、下载等数据先用于判断是否继续加功能。

### 应该暂缓
- 大量新增滤镜控制项、贴纸分类、复杂文字排版、草稿系统、账号/云端同步。
- 在性能基线未稳定前引入大型框架或复杂状态库。
- 直接进入 iOS/Android App 商店级封装。
- 原生重写。

## 三阶段路线
### 短期：Web 核心体验稳定
目标：浏览器里先足够快、稳定、可导出。

任务：
- 完成 P0 丝滑性与滤镜渲染性能闭环。
- 吸收 UX Lab 复盘：不再把 P0 主要希望押在继续调 debounce/降采样参数上，而是先确认架构瓶颈。
- 建立真机/内嵌浏览器验收清单：Safari、Chrome、微信、小红书、低端 Android WebView。
- 做资源体积盘点，明确首屏资源、延迟资源和可删除/可子集化资源。
- 把 Web 入口事实写清：短期仍以 `src/app.js` 为生产入口，旧模块只作为迁移参考。
- 功能上做减法：移动端优先保留高频控件，低频高级项暂缓或折叠。

验收：
- 低端手机拖动滑杆和移动图层时不被完整滤镜重算打断。
- 导入、编辑、导出在主流移动浏览器可完成。
- 首屏不被字体和贴纸资源拖慢。

### 中期：工程结构和 PWA 试验
目标：让 Web 可维护、可安装、可缓存。

任务：
- 确立模块化迁移顺序：先抽配置与纯函数，再抽渲染管线，再抽 overlay/UI，最后切入口。
- 引入最小构建流程的可行性评估：优先考虑 Vite 原生 ESM，不急于引入组件框架。
- 设计 PWA manifest、图标、Service Worker、离线兜底页和资源版本策略。
- 建立浏览器回归脚本或最小 Playwright 检查：加载、上传样图、套预设、添加图层、打开导出预览。
- 建立性能指标：首屏 JS/CSS/字体体积、上传后首次渲染耗时、滑杆松手后清晰渲染耗时、导出耗时。

验收：
- PWA 可作为试验版本安装，不影响普通网页访问。
- 静态资源缓存可控，版本更新不会拿到旧字体/旧代码组合。
- `src/app.js` 开始有稳定拆分边界，新增功能不继续堆进主文件。

### 长期：App 壳或原生方案评估
目标：只在 Web 已证明核心体验成立后，选择最低成本的 App 路线。

判断依据：
- 是否需要系统级保存到相册、分享面板、文件管理、离线素材包。
- 是否需要规避内嵌浏览器限制。
- 是否需要 App Store/应用市场分发。
- WebView 中 Canvas 性能、内存峰值、导出保存是否达标。

推荐：
- 移动端优先 Capacitor：复用 Web 代码，补齐文件/分享/保存能力。
- 桌面端如有明确需求再看 Tauri；Electron 体积较大，除非需要成熟桌面生态能力，否则不优先。
- 原生重写最后考虑，只适合在 WebView 被真实数据证明无法达标时启动。

## PWA 和 App 封装判断
### PWA 适合的条件
- Web 核心体验已经稳定。
- 需要安装图标、离线打开、静态资源缓存。
- 不强依赖系统相册写入或复杂文件权限。

### Capacitor 适合的条件
- 移动端 Web 已经跑通，但浏览器保存/分享体验不稳定。
- 需要调用相册保存、系统分享、文件选择、状态栏、安全区等原生能力。
- 能接受 WebView 性能边界，并愿意做 iOS/Android 真机测试。

### Tauri/Electron 适合的条件
- 明确要桌面应用分发。
- 需要本地文件系统、菜单、快捷键、离线资源包。
- Tauri 优先于 Electron；Electron 仅在插件生态或兼容性明显更重要时考虑。

### 原生重写适合的条件
- WebView 的性能或内存被验证无法满足核心编辑体验。
- 有足够开发资源维护 iOS/Android 两套或跨平台原生技术栈。
- 产品已经稳定，不再频繁改 UI 和滤镜逻辑。
